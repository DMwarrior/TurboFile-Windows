# TurboFile 统一原生拖拽会话设计

## 目标

将文件列表与图片网格中的同侧拖拽、左右侧拖拽和拖到 Windows 桌面/资源管理器统一到一套拖拽会话控制器中。一次按住鼠标左键只允许存在一个拖拽会话；松开鼠标后该会话必须确定地进入成功、取消或失败终态，不再通过“Chromium 拖拽离开窗口后再接力到第二个原生拖拽”的方式工作。

## 根因

当前实现先启动 Chromium HTML5 拖拽，用 `application/x-turbofile-side` 等数据支持同侧和左右侧目标；当指针离开页面或到达窗口边缘时，再调用 Electron `webContents.startDrag` 启动 Windows OLE 拖拽。两个拖拽循环争用同一次鼠标按压，边界时序会导致以下偶发问题：

- 原 Chromium 拖拽尚未结束，Windows 原生拖拽已经尝试接管鼠标；
- 鼠标在接力过程中已经释放，原生拖拽看到的按键状态与页面状态不一致；
- 页面重绘或源行销毁发生在拖拽图像清理之前，产生长期残留的拖拽阴影；
- 外部目标捕获失败后，页面和主进程分别等待各自的结束信号，形成无响应或超时。

## 方案比较

### 方案 A：继续修补窗口边缘接力

改动最小，但仍保留两个拖拽循环和时序竞争。此前多次修补已经证明该结构无法稳定覆盖快速拖出、桌面、资源管理器和高 DPI 多屏边界。

### 方案 B：所有目标使用代理目录

无论本地还是 SSH 都拖动一个临时代理目录，再由应用接管实际复制。控制最统一，但会让本地文件拖到 Windows 失去 Shell 的真实文件拖拽快路径，并改变本地复制体验。

### 方案 C：统一会话控制器，按来源选择原生载荷（采用）

所有 TurboFile 拖拽都由同一个不可变会话快照管理，并且只启动一次 Windows 原生拖拽。本地复制到 Windows 使用真实文件路径，保留 Shell 快路径；SSH 来源或剪切模式使用带会话令牌的代理目录，由 CopyHook 捕获外部目录。落回 TurboFile 时，页面通过当前会话识别为内部落点，不把代理目录当作外部文件处理。

该方案同时满足稳定性、现有速度和现有复制/剪切语义，因此采用。

## 架构

### 会话快照

新增可测试的 `TurboFileNativeDragSession` 数据模型，包含：

- 唯一会话编号；
- 来源页面、来源侧与来源设备；
- 拖拽开始时冻结的复制/剪切模式；
- 冻结后的文件/文件夹清单；
- 状态：`preparing`、`dragging`、`dropped-internal`、`dropped-windows`、`canceled`、`failed`、`completed`；
- 可选内部落点：面板背景、文件夹或上一级；
- 可选 Windows 目标目录。

同一编辑器实例同一时间只允许一个活动会话。旧会话收到迟到事件时不得影响新会话。

### 渲染器控制器

文件行和图片卡片共用一个启动入口：

1. 固化当前选择、来源侧和复制/剪切模式；
2. 写入必要的 HTML5 数据作为兼容信息；
3. 立即启动一次原生拖拽，不再监听窗口边缘并二次启动；
4. 页面内部落点只记录会话的落点决策；
5. 原生拖拽结束后，在下一帧执行既有的同侧移动或左右传输函数。

同侧拖到文件夹或上一级始终是移动，不受工具栏复制/剪切模式影响。左右侧和拖到 Windows 使用拖拽开始时冻结的模式。

### 主进程原生拖拽

主进程继续使用 Electron `webContents.startDrag`，不恢复曾经失败的第二个 `TurboFileDragSource.exe` 进程：

- 本地复制使用真实路径载荷，保留 Windows Shell 原生性能；
- SSH 来源、本地剪切或需要应用接管的来源使用当前 CopyHook 代理目录；
- 原生拖拽返回后只进行短暂、确定的目标收敛，不留下 45 秒未决等待；
- 所有结束路径清理活动目录和目标文件；
- 迟到的 CopyHook 文件通过会话编号隔离，不能命中下一次拖拽。

### 内部落点处理

同侧文件夹、同侧上一级、左右侧面板和图片网格先检查活动会话。若命中：

- 同步 `preventDefault`，让 Windows 显示允许落下；
- 只保存落点快照，不在 `drop` 回调内重绘；
- 等原生拖拽循环退出后再执行移动/传输；
- 执行前再次校验会话仍为当前会话。

普通 Windows 文件拖入 TurboFile 没有活动会话，继续走现有外部路径提取与传输逻辑。

## 失败与清理

- `Escape`、无落点、窗口销毁和原生拖拽取消都进入 `canceled`，不传输、不删除源文件；
- CopyHook 未捕获目录时立即给出失败状态，不把代理目录当成实际传输源；
- 剪切仅在目标传输完整成功后永久删除源文件，不进入回收站；
- 同侧移动继续使用原生批量重命名；
- 所有状态清理都按会话编号执行，且允许重复调用；
- 页面重绘、目录刷新和源文件删除全部延后到原生拖拽图像完成清理之后。

## 测试

### 单元与静态回归

- 会话状态只能按允许的方向转换，旧会话不能结束新会话；
- 拖拽开始时冻结选择和复制/剪切模式；
- 同侧文件夹落点强制移动；
- 左右侧和 Windows 落点保留冻结模式；
- 内部落点不会被当成外部代理目录；
- 文件列表和图片网格复用同一个启动入口；
- 代码中不再存在窗口边缘二次启动入口；
- 主进程只使用 `webContents.startDrag`，不恢复辅助拖拽进程；
- 取消和失败不删除源文件，剪切成功后才永久清理。

### 编译与全量验证

- `npm run compile-check-ts-native`；
- TurboFile 全量单元测试；
- Windows 桌面应用验证本地/SSH 的单文件、多文件、文件夹和图片网格；
- 分别验证同侧文件夹、同侧上一级、左到右、右到左、桌面、普通资源管理器目录、取消与连续快速拖拽；
- 验证复制/剪切模式、进度显示、源目录刷新以及无残留阴影。

## 边界

- 不修改数据传输协议、并发数、缓冲区或速度计算；
- 不修改普通删除进入回收站的规则；
- 不修改快捷键复制/剪切/粘贴；
- 不增加后台预扫描或总大小计算；
- 不将本地真实文件的 Windows Shell 快路径强制改为代理目录。
