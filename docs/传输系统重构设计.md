# 极速传 传输系统重构设计（Transfer System v2）

> 状态：设计稿（实现依据）
> 范围：`src/vs/platform/turbofile/electron-main/turbofileSshMainService.ts`（传输引擎）、`src/vs/workbench/contrib/turbofile/browser/turbofileEditor.ts`（UI/入口）、`src/vs/platform/turbofile/common/turbofile.ts`（协议类型）
> 对标：WinSCP（https://github.com/winscp/winscp），SCP/SFTP 行为与传输逻辑完全对齐；rsync 使用内置二进制，按 rsync 原生最优方式运行

---

## 1. 目标与设计原则

1. **稳定压倒一切**：每条路线（协议 × 方向 × 直连/中转）有唯一、确定、可追溯的执行路径；失败时按固定降级链回退，绝不静默换协议导致"显示 scp 实际卡死"这类问题。
2. **零预计算启动**：rsync 路线一律不做大小/文件数预扫描，进程毫秒级拉起；"准备中"只允许出现毫秒级。
3. **进度永不冻结**：进度要么来自协议自身的真实输出（rsync progress2、SFTP/SCP 字节计数），要么由 UI 1s 心跳兜底（已用时间持续跳动），任何时刻界面都不允许静止。
4. **乐观直连**：默认按直连发起，短超时快速失败后自动切中转，并缓存判定结果，不做提前探测。
5. **WinSCP 对齐**：SCP/SFTP 的协议细节、拖拽/剪贴板交互逻辑均以 WinSCP 源码为准（具体模块映射见 §5、§8）。
6. **协议选择可预期**：设备管理中选择的协议必须严格生效，两端设备协议不一致时按 §6 的确定性规则协商，规则写死、可解释。

---

## 2. 现状问题清单（重构动机）

| 问题 | 根因 | 对应章节 |
|---|---|---|
| rsync 长时间"准备中"不进入传输 | 启动前做预扫描 / 起始事件用 `prepare` 相位 / 静默 file-list 扫描期无渲染 | §5.3、§7 |
| rsync 进度不显示 / 卡 0 | 依赖总量才能算百分比；总量为 0 时节流逻辑失效造成事件洪泛 | §7 |
| 协议显示与实际不符（显示 scp 实际 rsync 失败回退） | 决策分散在多个 try 函数里，失败静默 fallback | §4、§6 |
| 首次/重复传输速度差异大 | 预扫描 + 事件洪泛拖慢主进程 | §5.3、§7 |
| 直连失败时长时间挂起才转中转 | 直连探测/超时不统一 | §4 |
| 设备协议设置部分场景不生效 | upload 看 target、download 看 source，ssh↔ssh 两端规则不统一 | §6 |

## 3. 总体架构

### 3.1 分层

```
┌─────────────────────────────────────────────────────────────┐
│ UI 层 turbofileEditor.ts                                     │
│  入口统一收敛为 2 个：剪贴板(Ctrl+C/X/V)、拖拽(DnD)            │
│  产出 TransferIntent（源条目集合 + 目标目录 + copy/move）      │
├─────────────────────────────────────────────────────────────┤
│ 渲染进程服务 turbofileSshService.ts（IPC 代理，不含逻辑）       │
├─────────────────────────────────────────────────────────────┤
│ 主进程引擎 turbofileSshMainService.ts                         │
│  ① 计划层 resolveTransferPlan()：唯一决策入口（§4/§6）         │
│  ② 路线层 RouteExecutor：direct / relay 两种执行器             │
│  ③ 协议引擎层：SftpEngine / ScpEngine / RsyncEngine / TarEngine│
│  ④ 进度总线 fireTransferProgress（500ms 节流 + 完成必发）      │
└─────────────────────────────────────────────────────────────┘
```

**核心重构点：决策与执行分离。** 现状是 `transferFile`/`transferBatch` 里层层 try 各协议；v2 改为先由 `resolveTransferPlan` 一次性算出 **有序执行计划**（协议 + 路线的降级链，最多 3 项），执行层只按计划逐项执行，每次降级都向 UI 发事件（用户能看到"直连失败，已切换中转"），最终上报的 `strategy` 必须是真实执行成功的那一项。

### 3.2 计划结构（新增类型，`turbofile.ts`）

```ts
interface ITurboFileTransferPlan {
	readonly attempts: readonly ITurboFileTransferAttempt[]; // 有序，第一项失败才尝试下一项
}
interface ITurboFileTransferAttempt {
	readonly protocol: 'sftp' | 'scp' | 'rsync' | 'tar';
	readonly route: 'local' | 'direct' | 'relay';   // local = 本机↔ssh 或 同机
	readonly reason: string;                         // 决策原因，写入任务日志
}
```

## 4. 路线判定：乐观直连 + 失败降级中转

适用于 ssh↔ssh 传输（本机↔ssh 天然"直连"，无此问题）。

### 4.1 规则

1. **不做预探测**。除非 `strategyHint === 'relay'`，第一次尝试一律按直连发起（源端直接连目标端，沿用 `resolveDirectSshRoutes` 产出的候选路线：source-push / target-pull）。
2. **快速失败窗口**：直连尝试的 TCP/SSH 建链超时 **5s**；建链成功但 **10s 内无首字节进度** 视为路线不通（沿用 `DIRECT_TRANSFER_STALL_TIMEOUT_MS` 机制，但仅对"0 字节阶段"生效——一旦有数据流动，不再因此超时）。
3. **失败即降级**：直连失败立刻切换同协议的中转路线（`getSshToSshRelayStrategy`），并发进度事件告知 UI（`detail: 'direct failed: …, falling back to relay'`）。
4. **结果缓存**：按 `(sourceDeviceId, targetDeviceId)` 缓存路线判定结果，TTL **10 分钟**：
   - 直连成功 → 后续传输直接走直连（命中缓存时建链超时仍然生效，失败则刷新缓存为 relay）；
   - 直连失败 → TTL 内后续传输直接走中转，**不再重试直连**（避免每次都白等 5s）；TTL 过期后下次重新乐观尝试直连。
   - 缓存仅存内存（Map），进程重启即清空，不持久化。
5. 用户在设备管理中显式选择的 `strategyHint`（direct/relay）优先于缓存。

### 4.2 不变量

- 直连与中转使用**同一个协议引擎**，只是 SSH 通道搭建方式不同（中转 = 本机起隧道/落地缓存），保证两条路线行为一致。
- 任何降级都必须出现在任务日志里（协议名 + 失败原因 + 降级目标）。

## 5. 协议引擎

### 5.1 SFTP 引擎（对齐 WinSCP `TSFTPFileSystem`）

WinSCP 参考：`source/core/SftpFileSystem.cpp`、`source/core/CopyParam.cpp`。

| 项 | 设计值 | WinSCP 依据 |
|---|---|---|
| 协议版本 | 协商 SFTP v3–v6，按服务端最高 | `FVersion` 协商 |
| 读写块大小 | 32 KB 起步，自适应放大到 256 KB（`SFTP_MAX_PACKET` 内） | `TSFTPFileSystem::UploadBlockSize` |
| **请求流水线** | 同一文件保持 **32 个并发未决读/写请求**（pipelining），不等上一块 ACK | `TSFTPUploadQueue` / `TSFTPDownloadQueue` |
| 属性同步 | 仅 mtime（`SSH_FXP_SETSTAT`），不改 owner/perm（与 rsync 选项口径一致） | `--no-perms` 等价 |
| 断点续传 | ≥10 MB 文件支持 `.filepart` 续传（写临时名，完成后 rename） | WinSCP ResumeSupport |
| 目录创建 | 逐级 `SSH_FXP_MKDIR`，已存在不报错 | `TSFTPFileSystem::CreateDirectory` |
| 覆盖语义 | 默认覆盖（与现有 UI 行为一致） | — |

实现说明：当前 ssh2 库的 `sftp.fastGet/fastPut` 已内置并发分块（`concurrency`、`chunkSize` 参数），优先配置 `{ concurrency: 32, chunkSize: 262144 }` 达到 WinSCP 等效流水线，不必手写队列。

### 5.2 SCP 引擎（对齐 WinSCP `TSCPFileSystem`）

WinSCP 参考：`source/core/ScpFileSystem.cpp`。

- **协议**：经 SSH exec 通道运行远端 `scp -t`（上传）/`scp -f`（下载），实现 SCP1 协议：`C<mode> <size> <name>`、`D`（目录进入）、`E`（目录退出）、`T`（mtime），每条消息后等待 `\0` ACK——与 WinSCP 完全一致。
- **递归目录**：用 `D/E` 消息流式递归，**不需要预先统计总大小**——但单文件场景源大小已知（`fs.stat`/`SSH_FXP_STAT` 一次调用），所以 scp 的"已传/总量 + 剩余时间"显示数据天然可得（见 §7）。
- **块大小**：源读取 buffer 256 KB，写入通道背压驱动（`stream.write` 返回值 + drain），不额外节流。
- **mtime 保留**：发送 `T` 消息（等价 `scp -p`）。
- **本机↔ssh 单文件**（auto-fast 的快路径）保持现状不动——这是当前唯一"完全正常"的路径，重构时**冻结其行为**，仅允许把决策入口换成 `resolveTransferPlan`。

### 5.3 rsync 引擎（内置二进制，零预扫描）

二进制：`resources/turbofile/rsync/win32/`（MSYS2 rsync 3.4.3 + OpenSSH 10.3，askpass 用 `.cmd` 方案，已落地）。

**拓扑（关键设计，全部由本机 rsync 进程驱动）：**

| 方向 | 命令形态 |
|---|---|
| 本机 → ssh | 本机 rsync **推**：`rsync [opts] <local…> user@host:<dir>` |
| ssh → 本机 | 本机 rsync **拉**：`rsync [opts] user@host:<remote…> <localdir>` |
| ssh → ssh 直连 | 源端 rsync 推目标端（经 `resolveDirectSshRoutes`，源上必须有 rsync） |
| ssh → ssh 中转 | 本机起端口转发隧道，本机 rsync 经隧道桥接（`tryTunneledRsyncRelayTransfer`，已落地） |

**诚实约束（文档必须写明）**：rsync over SSH 要求**远端也存在 rsync 可执行文件**（远端跑 `rsync --server`）。"内置 rsync"解决的是**本机**不需要安装；远端缺 rsync 时（`capabilities.rsync === false`），auto-fast 自动降级 scp（多文件逐个）或 tar 流，**不弹窗、不要求安装**，仅在任务日志记录降级原因。能力检测沿用 `detectCapabilities` 的缓存结果，不在传输路径上现场探测。

**启动纪律（Bug 修复成果固化为规范）：**

1. 进入 rsync 路径后 **禁止任何** `du`/递归 stat/文件计数预扫描；唯一允许的预操作是对每个顶层源条目一次 `lstat`（区分文件/目录，构造参数用，微秒级）。
2. 远端目录创建用 `--rsync-path="mkdir -p '<dir>' && rsync"` 内联完成，不走 SFTP 预建目录。
3. spawn 之后**立即**发 `phase: 'transfer'` 起始事件（不是 `prepare`），`totalBytes: 0`。
4. rsync 自身的 file-list 增量扫描静默期由 UI 心跳兜底（§7）。

**固定参数（当前实测最优，固化）：**

```
-a --inplace --whole-file --no-compress --numeric-ids -s
--no-perms --no-owner --no-group --omit-dir-times
--timeout=600 --info=progress2 --outbuf=N
ssh 传输层: -T -x -o Compression=no -o ServerAliveInterval=15
```

- `--whole-file --no-compress`：局域网最优（差量计算与压缩都是 CPU 瓶颈）；
- `--inplace`：免去临时文件 rename，目标盘满风险低、速度稳定；
- 禁止加回 `--partial-dir`、并行多进程 rsync、百分比反推总量等历史方案（均已被实测否决）。

**进度解析**：仅取 `--info=progress2` 输出的**已传字节数**（`parseRsyncProgressSnapshot(buffer).bytes`），可解析到 `to-chk`/`xfr#` 时附带 `toCheck/totalChecks` 供 UI 显示文件计数，**绝不**用百分比反推总量。

### 5.4 tar 流引擎（ssh↔ssh 备选）

保持现状（`tryTarRelayTransfer` / batch tar）：源端 `tar c` 管道至目标端 `tar x`，仅在 设备协议=tar 或 rsync/scp 均不可用时启用，Windows 路径不适用。不在本次重构范围内做行为变更。

## 6. 协议选择矩阵（设备设置如何生效）

设备协议设置入口：设备管理表单 `preferredTransferProtocol`（`turbofileTypes.ts`，含本机虚拟设备的 `turbofile.localWindows.preferredTransferProtocol` 存储键）。

### 6.1 决定权规则（确定性，写入 `resolveTransferPlan`）

1. **本机 ↔ ssh**：由 **ssh 端设备** 的协议设置决定（上传看 target、下载看 source，与现状一致）。本机虚拟设备的协议设置仅在"本机↔本机"场景使用。
2. **ssh ↔ ssh**：
   - 两端设置相同 → 用该协议；
   - 任一端为 `sftp` → 用 **sftp**（sftp 是用户显式要求的最保守选项，必须无条件尊重）；
   - 一端 `auto-fast`、另一端具体协议 → 用具体协议那端的设置；
   - 两端是不同的具体协议（如 A=rsync、B=scp）→ 按保守序取交集：`sftp > scp > tar > rsync`，选**更保守**的那个，并在任务日志记录"两端协议不一致，已采用 X"。
3. **能力裁剪**：协商结果若远端能力不支持（`capabilities`），按 §6.2 降级链下移，决不静默失败。

### 6.2 auto-fast（智能极速）展开表

| 场景 | 第 1 选择 | 第 2 选择 | 第 3 选择 |
|---|---|---|---|
| 本机↔ssh，单文件 | **scp**（现状快路径，冻结） | sftp | — |
| 本机↔ssh，多文件/含目录 | **rsync**（本机推/拉） | scp 逐项 | sftp 逐项 |
| ssh↔ssh，单文件 | scp 直连 | rsync 直连 | 同协议中转 |
| ssh↔ssh，多文件/含目录 | rsync 直连 | tar 直连 | rsync 中转 |
| 本机↔本机 / 同机 ssh | 原生复制（`local-copy`/`remote-copy`） | — | — |

显式选择具体协议时**不跨协议降级**（用户选了 rsync 就只在 rsync 的直连→中转内降级，失败就报错），只有 auto-fast 才允许跨协议降级——这保证"设备协议选择必须生效"。

### 6.3 strategy 上报

`ITurboFileTransferResult.strategy` 与进度事件的 `strategy` 必须等于**实际执行成功的 attempt**，UI 状态栏协议徽标（如"scp 直连"）直接渲染该值，杜绝显示与实际不符。

## 7. 进度与时间显示规范

### 7.1 两套显示模板（状态栏右侧）

| 协议族 | 模板 | 示例 |
|---|---|---|
| scp / sftp / tar（总量已知或可低成本得知） | `实时速度 │ 剩余时间 │ 已传/总量 │ 协议` | `117.2 MB/s │ 17.2s │ 1.1 GB / 3.0 GB │ scp 直连` |
| rsync（总量未知，零预扫描） | `实时速度 │ 已用时间 │ 已传大小 │ 协议` | `96.4 MB/s │ 12.3s │ 1.2 GB │ rsync 直连` |

- rsync 在 0 字节静默扫描期显示 `扫描文件中… │ 已用时间`（已落地）；
- scp/sftp 的"总量"：单文件 = stat 一次；批量 = 用 UI 已有的列表元数据求和（文件列表里 size 已知，**不新增磁盘扫描**；含目录的批量若总量未知则该任务整体退为 rsync 模板显示）。

### 7.2 数据来源

- **速度**：统一由进度总线按事件间字节差计算 3s 滑动窗口均值（`speedBytesPerSecond`），所有协议同一算法；
- **剩余时间**：`(total - transferred) / speed`，仅总量已知时显示；
- **已用时间**：`Date.now() - transferStartedAt`，由 UI 1s 心跳 ticker（`updateLiveTransferTicker`，已落地）保证持续跳动。

### 7.3 节流与完成事件（固化既有修复）

```
节流窗口 TRANSFER_PROGRESS_EVENT_INTERVAL_MS = 500ms
必发事件：首个数据事件(isFirstDataProgress)、完成事件(isCompletionEvent)、force=true 的相位切换
totalBytes=0 时 isCompletionEvent 判定必须含 normalizedTotal > 0 守卫（防事件洪泛拖慢传输，回归测试覆盖）
```

### 7.4 时间格式（全局统一，`formatDuration`）

- 秒级一律 1 位小数：`0.3s`、`1.0s`、`2.3s`；**禁止** `<1s`、`X ms`；
- ≥60s：`m:ss`；
- 适用范围：状态栏、任务日志、完成提示，全部走同一个 `formatDuration`。

## 8. 传输入口（仅两种，统一收敛）

两个入口最终都产出同一个 `TransferIntent`，走同一条 `transferBatch` 管线——入口只负责"确定源条目 + 目标目录 + copy/move"，不做任何协议决策。

### 8.1 剪贴板（Ctrl+C / Ctrl+X / Ctrl+V）

WinSCP 参考：`source/forms/CustomScpExplorer.cpp`（ClipboardOperation）、`source/windows/GUITools.cpp`。

| 操作 | 行为 |
|---|---|
| 软件内复制（任一面板 Ctrl+C/X） | 写**应用内剪贴板**（源端点 + 条目列表 + copy/move 标记）；若源是**本机文件**，同时写系统剪贴板 `CF_HDROP` + `Preferred DropEffect`，使 Explorer/桌面可直接 Ctrl+V（与 WinSCP 一致） |
| 软件内粘贴（Ctrl+V 到面板） | 优先消费应用内剪贴板；否则读系统剪贴板（`readWindowsClipboardFiles`，含 DropEffect → copy/move），实现 Explorer → 软件粘贴 |
| 同面板/同设备粘贴 | 走同机策略（`local-copy`/`remote-copy`），Ctrl+X 为 rename/mv 快路径 |
| 远程文件 Ctrl+C → Explorer 粘贴 | 与 WinSCP 同口径：**不支持**直接系统级粘贴（远程内容无本地路径）；应用内剪贴板照常可用，系统剪贴板写入远程路径文本（方便粘贴路径）。后续增强（P4，可选）：复制时向系统剪贴板写延迟渲染的虚拟文件（`CFSTR_FILEDESCRIPTORW/FILECONTENTS`，需原生模块） |
| Ctrl+X 语义 | 粘贴成功后删除源（`operation: 'move'` 走引擎的 move 清理逻辑），任何一项失败则该项源**不删除** |

### 8.2 拖拽（DnD，逻辑对齐 WinSCP）

WinSCP 参考：`source/windows/DragDrop.cpp`、`source/dragext/`（shell 扩展）、`source/forms/CustomScpExplorer.cpp` 的 DDDragEnter/DDDrop 系列。

| 方向 | 行为 |
|---|---|
| 面板 ↔ 面板 | HTML5 DnD（现状 `application/x-turbofile-side` 标记），drop 即产出 TransferIntent；默认 copy，按住 Shift 为 move（WinSCP 同机默认 move、跨机默认 copy 的规则照搬：**同设备拖拽默认 move，跨设备默认 copy**，Ctrl 强制 copy、Shift 强制 move） |
| 同面板内 | 拖到文件夹行 = 移入该文件夹；拖到".."/上一级行 = 移到父目录（WinSCP 同机拖拽语义） |
| Explorer/桌面 → 软件 | drop 事件读 `dataTransfer.files` 真实路径，产出 上传 TransferIntent（已支持，保持） |
| 软件 → Explorer/桌面（本机文件） | `dragstart` 时调用 Electron 原生拖拽（`startWindowsFileDrag` 现状路径），交真实路径，Explorer 自行完成复制 |
| 软件 → Explorer/桌面（远程文件） | **WinSCP 无 dragext 时的同款方案**：dragstart 时把远程文件**下载到临时目录**（`%TEMP%\turbofile-dragout-<uuid>\`），下载经任务进度条展示，完成后以临时路径发起原生拖拽；大于阈值（200 MB）时弹确认。P4 增强：原生 `IDataObject` 虚拟文件实现 drop 时才流式下载（等价 WinSCP dragext 体验） |

### 8.3 入口层禁止事项

- 入口不得调用 `calculatePathSize` 等任何阻塞扫描；
- 入口不得自行选择协议/路线（曾导致"显示 scp 实际 rsync"类不一致）；
- drop/paste 后 100ms 内必须出现任务条目（哪怕引擎还没 spawn）。

## 9. 性能参数总表（最优固化）

| 层 | 参数 | 值 | 备注 |
|---|---|---|---|

## 10. 不可破坏清单（每次改动的回归红线）

1. scp 单文件快路径的速度与显示（当前基准：千兆局域网 ~110 MB/s）；
2. SSH 上传/下载、取消传输（`cancelTransfer`）、任务日志、传输完成后的文件列表自动刷新；
3. rsync 增量语义（重复传输只传差异）；
4. 本机↔远端↔远端三类路线现有可用性；
5. SSH 终端、图片预览/排序等非传输功能；
6. 时间格式规范（§7.4）与"永不冻结"原则（§1.3）。
